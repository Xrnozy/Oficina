# Oficina — detailed guide

The in-depth reference for Oficina: how the workflow engine, routing, checkpoints and commits behave. For an overview, screenshots and setup, see the [main README](../README.md). Design background: [`spec/AI-Agent-Office-Spec.md`](../spec/AI-Agent-Office-Spec.md).

## Quick start

```bash
npm install
npm run build -w ui     # build the React UI into ui/dist
npm run dev             # start the daemon on http://localhost:4780 (serves API + UI + WebSocket)
```

Then open http://localhost:4780 — the Dashboard has a "new run goal" box. The seeded **Demo Office** workspace comes with five scripted agents (PM, Developer, Reviewer, Analyst, Docs) and a demo repo; create a run, approve the DoD in the Approvals inbox, and watch the loop run plan → assign → build → verify → review → merge → done.

```bash
npm run seed            # re-seed the demo workspace (idempotent — skips if data exists)
npm run dev:ui          # optional: Vite dev server with HMR (proxying to :4780)
```

## Windows launchers

- `start-office.bat` — double-click: starts the daemon in a console window and opens the UI.
- `start-office-tray.bat` — double-click: runs the daemon hidden and puts an icon in the system tray. Right-click the tray icon → **Open Oficina** or **Quit Oficina** (Quit stops the daemon).

## Adding a backend (Providers page)

- **Claude Code / cursor-agent / Devin CLI (no API key)** — kind `cli`; uses each CLI's own login. Add backend detects which of these is installed on this machine and fills the command (pick one if several are installed). The Model list is read from the CLI itself:

  | Preset | Command | Models from | Prompt via |
  |---|---|---|---|
  | Claude Code | `claude -p --verbose --dangerously-skip-permissions --output-format stream-json` | `claude -p /model` | stdin |
  | cursor-agent | `agent -p --output-format stream-json --force` | `agent --list-models` | stdin |
  | Devin CLI | `devin -p --prompt-file {promptFile} --permission-mode dangerous --respect-workspace-trust false` | `devin models list --format json` | `{promptFile}` (Devin doesn't read stdin) |

  An empty Command still falls back to the Claude Code command. The chosen model is passed as `--model` (or wherever `{model}` appears). Other placeholders: `{prompt}` (inline, passed as one quoted argument), `{worktree}`.

  A CLI run ends at the backend's timeout (`timeoutSec`, default 900 s). A CLI that streams JSON events (Claude Code, cursor-agent) is also stopped earlier when it has stalled: no output for `idleTimeoutSec` (default 300 s) while no tool call is running. The work item is then retried like any other transient failure. Set `idleTimeoutSec` per backend through `PUT /api/providers/:id`; `0` turns the stall check off, and plain-text CLIs only get it when it is set explicitly. The daemon adds `%LOCALAPPDATA%\cursor-agent`, `%LOCALAPPDATA%\devin\cli\bin`, `%USERPROFILE%\.local\bin` and `%APPDATA%\npm` to PATH when spawning; an explicit executable path in the command is used as written. Log in first: `claude auth login`, `agent login`, `devin auth login`.
- **Devin** — kind `devin`. No CLI exists; Devin runs in Cognition's cloud over the REST API. Get a key at app.devin.ai → Settings → API Keys (starts with `cog_`). Devin returns work by pushing a `devin/…` branch to the repo's `origin` remote, so code delivery needs a remote Devin can reach (e.g. GitHub); for local-only repos you get its report but not files.
- **Model APIs** — kind `openai-compatible` (OpenAI/Ollama/LM Studio) or `anthropic` (API key). Keys are stored in `daemon/data/secrets.json` (git-ignored) — never in the repo.

Then point an agent at the new backend on the **Agents** page (backend dropdown on each card).

## Project profile and detected checks

When a repository is registered, and again at the first plan of every run, Oficina reads its manifest files to find what it is built with. No model is involved and nothing is run except `<tool> --version` probes. A repository can hold several stacks, each in its own folder (for example a Python backend, a React dashboard and an Android app), up to four folders deep. Dependency and vendored folders (`node_modules`, `vendor`, `third_party`, …) are skipped, and a build that another toolchain drives (CMake under Gradle for the NDK, C# projects generated by Unity) is not counted as a separate stack.

| Kind | Recognised from | Checks it offers |
|---|---|---|
| Node.js / TypeScript | `package.json` (npm, pnpm, yarn, bun) | its `build`, `typecheck`, `lint`, `test` scripts |
| Python | `pyproject.toml`, `setup.py`, `requirements*.txt` | `pytest` when tests exist; `ruff`, `mypy` when configured |
| Rust, Go, .NET, Java (Maven/Gradle), Android, Swift, Flutter/Dart | their manifests | build and test (`cargo`, `go`, `dotnet`, `mvnw`/`gradlew`, `swift`, `flutter`) |
| C/C++ | `CMakeLists.txt`, `Makefile` | configure + build (+ `ctest` when tests are declared); build output goes to the temp folder, never into the repository |
| Embedded / IoT | `platformio.ini`, ESP-IDF, Arduino `sketch.yaml`, Zephyr, MicroPython, embedded crates and toolchains | firmware build; host tests only (`pio test -e native`). Uploading, flashing or on-device tests are never run |
| Games | Unity, Unreal, Godot, and engines in `package.json`, `Cargo.toml`, .NET or Python | Godot with GUT runs its tests. Unity and Unreal need the editor, so the profile says which check to add |

**Domains.** Dependencies and repository signals (containers, Kubernetes, Terraform, migrations, API specs, CI) also give each stack a domain: embedded/IoT, game, service/enterprise, web, mobile, data/ML or native. The prompts for planning, implementation, fixes, QA, review and failure analysis carry a short *Project profile* section with two parts:
- the stacks the task works in (picked from its `affectedPaths`);
- for each of their domains, the concerns that matter there, such as memory, interrupt safety, bounded waits and hands off hardware for IoT, the frame budget and `.meta` files for games, or backward-compatible APIs and schemas plus secrets from the environment for services.

A project with a single stack at its root and no particular domain gets no profile section.

**Detected checks** are registered only when you configured none for the repository (no command checks of your own, no build/test command on the repo). Each is named after its scope: `unit:all` and `build` at the root, `unit:backend` or `build:mobile` for a stack in a folder. A folder-scoped check runs only when that folder changed, and none runs for a change that touched only documentation or media. Only checks whose tool is installed here are registered. Detected checks run with `CI=1`, so test runners run once instead of starting in watch mode.

**Baseline.** At the start of a run every detected check is measured once on the repository as it is, in the background while the PM plans. It is not measured again while the tree is unchanged. A check that already fails there still exists and the PM is told about it, but it does not gate deliveries, so no agent is sent to fix a failure it did not cause. In direct mode, the first writer waits for the baseline to finish (bounded), because the baseline runs in the same working tree. Results show up as `checks.detected` and `checks.baseline` in Live activity.

API: `GET /api/repos/:id/profile` returns the stacks, domains and checks with their baseline and whether they gate. Add `?detect=1` to detect again. To keep the engine from running a project's builds and tests on its own (for example when a cold build takes many minutes), set `PUT /api/workspaces/:id/settings { "detectChecks": false }`. The profile section still reaches the prompts.

## Flow: request → PM ⇄ Prompt Creator → developer → reviewer → PM

Send a feature request from **Requests**; every hand-off after that is automatic — prompts, change notes and findings travel between agents as structured messages and shared task context, never by copy-paste. Assign agents to roles on **Roles**, and pick their models on **Routing**.

| Step | Role | Does | Never |
|---|---|---|---|
| 1 | `pm` | turns the request into tasks + acceptance criteria | write, review or test code |
| 2 | `prompt-creator` | drafts the implementation-ready prompt | — |
| 3 | `pm` | reviews the draft (correct, complete, clear, aligned) — approves or sends it back | — |
| 4 | `developer` | edits the repository, self-checks, writes change notes (with a `Commit:` line) | — |
| 5 | `qa` / `reviewer` | checks the work against the **approved prompt**, the criteria and the tests; reports to the PM | edit code |
| 6 | `pm` | accepts (→ commit per policy) or reworks: the Prompt Creator drafts a **correction prompt**, the PM reviews it, the developer fixes | read code |

Check failures (build/tests) also become a correction prompt. The approved prompt stays the authoritative requirements: every correction, review and acceptance gets it, and it changes only when you edit the requirements. Loops are bounded (3 attempts, then you decide). The PM runs only when a decision is needed — planning, prompt approval, acceptance — never continuously. Each task keeps its full record (request → drafts → PM reviews → approved prompt → work → findings → corrections → checks → result) on its task page.

**Hand-offs are typed.** On every stage transition the engine writes a hand-off envelope (`{ fromRole, toRole, taskId, status, summary, filesChanged, checksRun, openQuestions, decisions, blockers }`, stored in `handoffs` and shown as `task.handoff` in Live activity). The next agent's prompt carries the envelope — not the previous agent's whole output. Full output is attached only when the recipient needs it (a fixer gets the findings; a reviewer gets the QA report when QA could not run or the accept step needs it).

**Decision roles answer in strict JSON.** The pm, prompt-creator, reviewer and qa replies are validated before they are acted on; a reply that fails validation gets exactly one automatic repair retry that sends back only the validation error and the bad output (the retry is a normal work item, so it shows up in the token report).

**Messages are delivered, not repeated.** Broadcasts reach each agent at most once (per-agent delivery tracking), messages on finished tasks are never delivered, and a message that is ≥90% the same as an unread one to the same recipient is dropped instead of re-sent.

**Prompt preparation** (Routing → Workflow): `pipeline` (default, as above; the PM drafts itself if there is no Prompt Creator), `handoffs` (PM writes only the task prompt; rework and check failures go straight to the developer — fewest calls), `all`, `off`.

## Visual workflow

The **Workflow** page draws the pipeline above as an editable graph — and lets you replace it. The built-in graph is a read-only mirror of the fixed pipeline; **Clone** makes your own copy, and **Set active** routes every new task in the workspace through it. Runs pin the workflow version they started on, so editing a graph never changes a run in flight. With no custom workflow active, nothing about the flow above changes (a suite test asserts the identical work-item sequence).

**Concepts.** The canvas holds *nodes* connected by *edges*; the engine walks the graph per task instead of following the fixed sequence. Saving creates an immutable version; activation points the workspace at the latest one. Each node can carry extra instructions, a model tier, a budget and per-node **skill attachments** (they take budget priority over the agent's and role's skills, and are frozen into the version they were saved with).

| Node | Purpose |
|---|---|
| `start` / `end` | entry and finish; every reachable path must reach an end |
| `agent` | a desk: role (or a pinned agent), purpose (plan/implement/qa/review/accept/analyse/doc/custom), scope (`run` — once per run — or `task`), instructions, budget, timeout, writable vs read-only, skill refs |
| `condition` | deterministic branch on outcome/task fields — no model call |
| `merge` | join parallel branches (`all` or `any` of its in-edges) |
| `human` | *Owner gate*: a plain pause for an owner decision, then continue |
| `approval` | *Human approval*: an agent launches your app and reports, then you approve (approve edge) or reject with feedback (reject edge) — see [Human approval](#human-approval) |

Edges: `next` (positive outcomes), `on-success`, `on-failure`, `on-reject` (the only kinds allowed to close a cycle — they carry a `maxLoops` bound, default 3, after which you decide), `message` (a structured note to the target node's agent — no model call; optionally `waitForReply`). Condition-node edges get a condition builder with a plain-language preview and exactly one `else` edge.

**Editing.** Drag agents (grouped by role) or Condition/Merge/Human/End from the palette onto the canvas. To insert an agent between two nodes, drop it onto the edge between them (or drag an existing node onto an edge, or click the edge's hover "+") — the edge splits and the first half keeps its kind and condition. Deleting a mid-chain node re-links its neighbours. Undo/redo, copy/paste, autosaved drafts, JSON import/export, version history with restore-as-draft. Validation badges mark the offending nodes; you can't save or activate a graph with errors.

**Safety.** The inspector shows a worst-case estimate (agent calls incl. loop bodies, human gates, skill chars) and **guardrails** — step, cost and time ceilings that pause dispatching on a *Needs you* item when hit. **Dry run** simulates the draft with mocked per-node outcomes — no model, no tokens — and highlights the taken path on the canvas. Templates (default, fast, strict, docs, bug-fix, parallel-review) give you a working starting point. Firing, editing or moving an agent that a graph references warns which workflow nodes are affected, and every edit lands in the hash-chained audit log on the version's page.

**While it runs.** Pick a run and the canvas lights up: rings show each node's step state and taken edges stay highlighted (from `workflow.step`/`branch` events, live over WebSocket or replayed for finished runs). Tasks record which node and edge produced each work item; a task stalled at a gate — human, exhausted loop, dead end, guardrail — appears under *Needs you* and resumes on your decision.

**Limits.** A run pins its starting version; conditions are deterministic (fields/operators, no free-form code); a `message` edge delivers to the target's next prompt rather than interrupting it; the run-scope `plan` node still runs through the engine's planning cadence, so re-planning on DoD review is unchanged.

## Offices

An **office** is a workspace with its own agents, desks (roles), workflows and runs. Pick the current office in the sidebar; Dashboard, Tasks, Live activity, Run replay, Routing, Workflow, Agents, Roles and *Needs you* all follow it, so each office sees only its own agents and its own flow. Providers, Skills and Error reports are shared across offices.

**Roles page.** Create an office **blank** (no agents, only the built-in pipeline) or **by copying** one: the copy gets *new* agents with the same roles and settings, and the source's workflows with their pinned agents remapped to the copies, so editing one office never touches the other. Rename or delete from the same page. An office with runs can't be deleted (the runs are kept for the record), and the last office can't be deleted; its agents stay and become available to other offices.

**Agents and offices.** The desks show only the open office's agents. *Available agents* lists everyone else; dragging one onto a desk adds it to this office (after the usual permission preview) and it keeps its desk elsewhere until you remove it with the × on its card.

**Export and import.** Two JSON formats, both portable between machines:

- `officechain.office` — the office's name, description and portable settings, its agents (name, avatar, instructions, observability, per-agent settings, roles) and its workflows. Import always creates a *new* office (a taken name gets a suffix) with new agents.
- `officechain.workflow` — one workflow. Export is on the Workflow toolbar; Import adds the file as a *new* workflow in the open office (from any view, including the read-only built-in one).

Agents are referenced **by name**, never by local id. On import a pinned step goes to the agent of that name in the target office (case-insensitive); if there is none it falls back to the step's role and the import reports which steps changed. Machine-specific things are not exported: backends, API keys and model fallbacks. Imported agents start on this machine's first enabled account, so check **Routing** afterwards.

## CLI sessions

A headless CLI run (`claude -p`, `agent -p`, `devin -p`) starts a brand-new conversation unless it is told to continue one, so without help every work item leaves another session behind. Oficina keeps a registry of CLI sessions and tells the CLI to continue one.

**One workflow node, one persistent session.** Each agent node keeps its own CLI session and continues it across tasks, retries, loop iterations and runs, so the agent keeps its understanding of the project. Separate nodes are separate conversations, even with the same agent, model or provider (PM and PM1 each have their own). Separate agents never share one: an agent that steps in on a node (fallback) gets a session of its own there. In the standard pipeline (no custom workflow) each agent is its own node. Work a graph run creates outside any node (a repair retry, the PM's diagnosis) continues that agent's node session. A session is keyed by workflow and node id, so saving a new version of the workflow keeps it.

A new session is started only when:
- a node (or a new agent on it) works for the first time;
- you press **Reset** on a session;
- you create one with **New session**;
- the CLI no longer has the conversation;
- the work moves to another backend or folder.

A CLI can continue only its own conversations, from the folder that started them, so the last two are unavoidable and are shown in Live activity. When the session is busy, because another task of the node is using it or you have it open in a terminal, the work waits its turn and says so. It never opens a second conversation, and a waiting work item isn't counted as stuck. Sessions from before this, and imported ones, become the node's session the first time it needs one, so existing conversations carry on.

**Per agent** (agent settings → *CLI sessions*, CLI backends only):

- **One session per workflow node** (default), as above.
- **New session every time**: nothing is tracked or reused.
- **Always one chosen session**: a specific session you pick, for example one you started yourself. It then belongs to this agent and node only; another agent pinning it gets its own instead.
- **Start a fresh session after N tasks** (default 0 = never): set it only if you want sessions retired after a number of tasks. Agents saved with the earlier defaults (an additional session when busy, a new one after 30 tasks) were moved to the new defaults once.

**Seeing and opening a session.** Click a session in the *CLI sessions* list to see:
- its node, agent, backend and session id, folder, status and number of tasks;
- **Conversation**: the CLI's own transcript, for Claude Code (read from `~/.claude/projects/…`);
- **Work**: every work item that ran in it, with the prompt sent and the reply;
- the exact resume command.

**Open in terminal** opens that same conversation in a new console window in its folder (`claude --resume <id>`, `agent --resume <id>`, `devin --resume <id>`). While the window is open the session is yours: the node's agent waits and continues the conversation, including what you added, once you close it. This survives a daemon restart. **Reset** archives the conversation; the node's next work starts a new one.

**How each CLI is driven** (checked against the real CLIs' help and error messages):

| CLI | New session | Continue | How the id is learned |
|---|---|---|---|
| Claude Code | `--session-id <uuid>` chosen by Oficina | `--resume <id>` | assigned up front |
| cursor-agent | none | `--resume <id>` | `session_id` in the JSON output |
| Devin CLI | none | `--resume <id>` | `devin list --format json` before/after the run (it lists the folder's sessions) |
| any other | *New-session arguments* on the backend | *Resume arguments* on the backend | those arguments, or a *session id pattern* applied to the output |

For a custom CLI, fill in the optional *Session reuse* fields when adding the backend (Providers). Without them such a CLI starts fresh every time, and the agent's drawer says so.

**Rules that keep this safe.** A CLI can only continue a session from the folder that started it, so sessions are tracked per folder and backend. A per-task worktree is a different folder every time, so work in isolated mode starts fresh and records nothing, which also means no clutter. If the CLI no longer has a session it is asked to continue ("No conversation found…" from Claude Code, "No session found matching…" from Devin), the session is archived and the work item is retried once with a new one, transparently. If a CLI never reports its session id the row is dropped instead of piling up. A restart clears any "in use" flags, except a terminal you still have open.

**Managing them.** The *CLI sessions* list on the Agents page shows each session's node, agent, folder, how many tasks it has served, when it was last used and whether it is in use. You can rename, assign to another agent (not while it is in use), archive/restore and remove sessions, press *New session* to prepare one for an agent ahead of time (its next node without a session takes it), and, for CLIs that can list their sessions (Devin), *Import* the ones that already exist in the repository; they arrive unassigned and the first agent that needs one claims it. Removing a session only forgets it in Oficina; the CLI keeps its own copy.

## Request queue

Prompts typed somewhere quick wait in a **per-office queue** that the whole app shares: the Dashboard lists it, and the Requests item in the sidebar shows how many are waiting in the open office.

**Adding.** Left-click the tray icon (Windows), type the prompt, pick the office and press Ctrl+Enter. The Dashboard's New request form also has **Queue for later**. A request is up to 8,000 characters and an office holds up to 200 queued requests. Over the API: `POST /api/queue { text, workspaceId, source }`, `GET /api/queue?workspaceId=`, `DELETE /api/queue/:id`.

**Starting.** Nothing runs just because it was queued. **Start…** on the Dashboard opens the New request form with the text filled in, so the repository, budget and workflow are chosen as usual; sending it consumes the queue item. Alternatively tick *Start the next one automatically when <office> is idle*: the daemon then starts the oldest queued request whenever the office has no run in progress (draft, DoD review, running, paused…), one at a time, using the office's first repository and the budget shown next to the checkbox (default $50). It is off by default. An office with no repository keeps its queue and waits, and with *confirm plan* on, a started run waits at DoD review, so the office counts as busy until you act.

**Tray.** The tray reads the daemon port from `daemon/office.yaml`, remembers the last office you queued into, keeps an unsent draft if you click away, and shows "<n> queued" in its status line and tooltip. The tray menu and popup follow the Windows light/dark theme by default; **Appearance** in the right-click menu switches them to Light or Dark and remembers the choice (stored in `%LOCALAPPDATA%\Oficina\tray.json` with the last office you queued into). The tray's code is in `office-tray.ps1` (the icon and daemon) and `office-tray-ui.ps1` (the menu and popup). Restart Oficina after updating so the daemon has the queue endpoints; an older daemon answers a quick request with a message saying so.

## Working in your repository (direct mode)

By default (**Routing → Where agents work → direct**) agents work inside the repository you selected, on the branch you have checked out, like a coding CLI — no copies of the project. `isolated` keeps the older worktree-per-task flow.

- Code tasks run one at a time, so every change is attributed to exactly one task and one agent.
- Uncommitted changes you already had are detected before a task starts (`repo.dirty`), preserved, and never included in the task's changes or commits.
- Nothing is created inside your repository for the office's own use: no `.office` folder, no `integration` branch, no extra worktrees, and your `.gitignore` and `.git/info/exclude` are not edited. The one thing you choose to put there is the `documents/` folder of reference files (see below). The developer's change notes live in the daemon's data folder (`data/handoff/<task>.md`), and checkpoints are Git objects pinned under `refs/officechain/`. (The worktree-per-task flow with its `integration` branch exists only in `isolated` mode.)
- The office never runs `reset`, `checkout`, `clean`, history rewrites or force-pushes.

### Checkpoints, undo and redo

- **General Checkpoint** — the whole result of a task (all its agents), recorded before and after the task.
- **Agent Checkpoint** — one agent's work item inside a task, recorded before and after it ran.
- **Manual Checkpoint** — a save point you create (Checkpoints → Save).

Undo / Redo / Restore move the working tree between two recorded states, **file by file**, after a dry run that shows each file's fate. Nothing is re-run and no model is called. For every file the preview says one of:

- **replace** — the file is exactly how the other side left it, so it is replaced or deleted;
- **merge** — you edited the file since, but not where this change was: the two sets of edits are merged and both kept;
- **blocked** — you edited the same lines, deleted the file, changed a binary, or a file or folder is in the way: the file is left exactly as it is and the reason is shown;
- **done** — the file is already how it should end up.

If anything is blocked the whole operation is refused and **nothing changes**; you can also choose *Undo the N safe files only*, which changes those and leaves the blocked ones untouched (the checkpoint stays "applied" until the rest is resolved, and running it again recognises what is already done). Folders an undo needs are created again, and folders it empties are removed — never a folder that still holds anything. Every write keeps a backup and is read back afterwards: if any step fails or any result differs from what was planned, every file is put back as it was. Later work touching the same files is listed as a dependency. Undoing a task takes its agents' checkpoints with it; undoing one agent leaves the rest. Restore first saves the current state, so it is reversible too.

**What a snapshot is.** A git tree object (tracked, untracked and deleted files; not ignored ones) built in a private index and pinned under `refs/officechain/`, so `git gc` keeps it; your index, branch and stash are never touched. When a checkpoint is created the snapshot is *proven* before anything relies on it: the tree must read back from git and the pinned ref must resolve to it (one retry from a fresh index, otherwise the checkpoint is refused rather than trusted). It records the branch and commit HEAD was on, how many files it holds, and the files it could not store (too large, or unindexable by git) — shown on the checkpoint, and never touched by undo or restore. Checkpoints left open by a crash are closed as `interrupted` on restart and stay undoable. Retention: the newest 500 per repository (`pruneCheckpoints`).

### Repository timeline

**Repo timeline** is a live picture of the repository, newest first and grouped by day: commits from **every local branch and tag, whoever made them** (an agent, VS Code, a terminal), General and Agent Checkpoints, undo/redo/restore, branch switches, amends and resets, new and deleted branches and tags, task results and reviews, and your Human-approval decisions.

- **Commits from outside the app.** The daemon watches each registered repository every few seconds (and again when you open the page). A commit made in VS Code appears as soon as it is seen, the page refreshes itself and says how many came from outside; commits made while the daemon was off are found on the next start. Commits the office made itself keep their *AI* label and link to their task and agents; everything else is yours (with its git author).
- **Context at the top:** the current branch, HEAD, how far ahead of or behind the remote you are, and a live count of uncommitted files (also as the first row of the timeline).
- **Filters:** search (commit messages, checkpoint and task names), an author menu, and Everything / Commits / AI / You / Checkpoints / Branches & history / Tasks & reviews. A side panel shows commits per day (AI vs yours) and the branches seen.
- Each commit shows its branches, tags, merge/HEAD badges and lines added/removed; click an entry for the actual diff. Commits can be reverted or reapplied (as new commits) after a dry run; two commits or two checkpoints can be compared. History rewrites are shown for what they are: the earlier commits are still in git's reflog.

### Commits

When the PM accepts a task, a commit containing **only that task's files** is prepared (`git commit --only -- <paths>`, so your hooks, signing and identity apply and anything you have staged stays staged). The message comes from the developer's `Commit:` line or the PM's acceptance — no extra model call. Generic titles are replaced with one derived from the task. Conventional Commits are used when the repository's history does. A trailer states only the verification that actually ran (`Checks: unit:all pass`, or `NOT VERIFIED` when something failed).

**Routing → Commits**: `approve` (default — the proposal waits under **Needs you**; edit the message on the task page), `auto` (committed when checks and review passed and only the task's files are involved; otherwise it asks), `manual`. A file you had already modified before the task, or edited after it finished, is never committed without your decision.

## Reference files and task attachments

**Reference files** are documents agents should follow: a `design.md`, a `spec.md`, coding standards, a screenshot of the target design. They are filed in your repository's **`documents/`** folder, arranged by who needs them, and handed to agents as a short list (name, kind, size, a one-line summary and the path). An agent opens only what its work needs, so a long document costs no tokens until it is read.

| Audience | Folder | Who is told about it |
|---|---|---|
| Every agent | `documents/all-agents/` | all agents in the office |
| Project Manager | `documents/pm/` | agents acting as PM |
| Developers | `documents/dev/` | agents acting as developer |
| Reviewers, QA, analysts, docs, prompt creator | `documents/reviewer/`, `qa/`, `analyst/`, `docs/`, `prompt-creator/` | agents acting in that role |
| One agent | `documents/agents/<name>/` | that agent only |
| One run | `documents/runs/<run>/` | every agent, during that run only |

Pick the audience when you add a file (Dashboard → *Reference files*, the *New run* form, Agents → an agent, or **+ → Upload documents** on Live activity); the folder is chosen for you. A file you already have in `documents/` is never overwritten (the new one gets `name (2).md`), re-adding a file with the same name in the same place updates it, and removing the last file removes the empty folders. These files are kept out of every task's changes, checkpoints, undo and commits; they show up in `git status` as untracked files, so you can commit them when you like. An office with no repository keeps them in the daemon's data folder instead. Files uploaded by an earlier version are moved into `documents/` on startup.

**The PM and routing.** The PM is told about every new file (in its inbox), sees what the other audiences were given, and can point a task at a document with `"references": ["design.md"]` in its plan; that file then reaches the task's agent whatever audience it was filed under. Prompts are rebuilt for every dispatch, so a file added mid-run reaches the next prompt: nothing running is interrupted and no task restarts.

**Task attachments** belong to one task (or one *work item* of it) and are seen only by the agents working it, so files never mix between tasks. They stay in the daemon's data folder, not in your repository. Drop a file onto a task card, into the **Ready** column (it starts a new task from the file), into *New task*, or on the task page's *Files* panel. A screenshot of a bug dropped into Ready becomes a task whose agent is given the image's path to open.

**Adding files without a file picker.** **+ → Upload documents** opens a panel right under the Live activity chat: drop files, browse, paste a screenshot (Ctrl+V), or switch to *Write a note* and type or paste Markdown, which is saved as a `.md` file for the audience you chose.

**Limits and checks.** Markdown, text, JSON/YAML/CSV, source and script files, images, PDF and Office documents, up to 10 MB each, 30 files per task, 200 per office. Executables are refused, a file whose bytes are binary but whose name says text is refused, names are stripped of folders, and files are served back with a sandboxing Content-Security-Policy. API: `POST /api/attachments?workspaceId=&scope=project|role|agent|task&role=&agentId=&taskId=&itemRef=&runId=&name=` (body = the file's bytes), `GET /api/attachments`, `PUT /api/attachments/:id` (replace), `DELETE /api/attachments/:id`.

## The Tasks board

Columns: **On hold**, **Ready**, **In progress**, **In review**, **Done**, **Failed / blocked**.

- **Only two columns are yours.** Drag a card between *On hold* and *Ready* (or use the pause / play button on the card). *In progress, In review, Done* and *Failed* are facts the workflow produces from what the agents actually did, so they can't be dropped on, and the API refuses to set them (`POST /api/tasks/:id/move` accepts `ready` and `held` only). A task an agent has already started can't be put on hold.
- **On hold** keeps a task on the board without any agent picking it up. A run can finish while tasks are on hold; if only held tasks remain, the run waits quietly (it never re-plans the work you parked) and a note tells you. A task that others wait for can't be held until they are.
- **Delete** (trash button, or on the task page) removes a task with its attached files, prompts, check results and messages, and un-blocks tasks that waited for it. It is refused while an agent is working on it. The repository, commits and checkpoints are never touched; undo changes from Checkpoints.
- **New task** (Tasks page or **+ → Create a task**) takes a title, background, **work items** and files. Each work item is a specific thing to do, with optional instructions and its own files; every item becomes an acceptance criterion the agents check and appears in every prompt for the task. *Put on hold* saves it without handing it to the agents.
- A task you add during a run enters as *ready* and the next free, eligible agent takes it through the normal PM-reviewed prompt flow. The run isn't marked done while one is open.

## Request intake

The **Request** node (the start of every workflow) can name an agent that analyses and checks a request before any run exists. Pick it in the Workflow editor (select the Request node → *Analyse the request with*); **New run** preselects it, and you can choose another agent, or none, for a single request (*Analyse the request with* in the side panel; not used for one-shot runs).

1. **Describe** — write what you need and attach files as usual, then press *Analyse request*. Files are saved first so the agent can open them.
2. **Review** — the agent replies with a short summary, items grouped as Features, Technologies, Issues to fix, References and Constraints, and a *Worth checking* list of what is unclear, risky, missing or contradictory. Every item has three possible states:
   - **kept** (tick it, edit its wording, or add your own) — fixed: no later pass changes, rewords, splits or repeats it;
   - **open** — the agent's proposal nobody has judged yet; the only items a later pass may sharpen, replace or drop;
   - **removed** — never suggested again, in the same words or an equivalent; it can be restored from the *Removed* list.
3. **Iterate** — type more details (or press *Answer* next to a question) and *Update the summary*: the agent only adjusts the open items and adds what is new (marked *updated*). Edit the request text itself from the side panel. As many passes as you like.
4. **Approve** — *Approve and start* creates the run. Its goal is your text followed by the reviewed breakdown (kept and open items, your extra details, and the items you ruled out marked *do not do these*), so the PM plans from exactly what you agreed. *Discard* drops the draft and the files uploaded for it.

These rules are enforced by the engine, not left to the model: it restates your decisions in every prompt, and merges the reply itself — an agent that rewrites a kept item or revives a removed one is ignored for that item (the merge is `mergeItems` in `daemon/src/services/intake.ts`). The reply must be a JSON object; a malformed one is retried once, then the draft shows an error and you can try again or approve your request exactly as typed.

**Its own CLI session.** Each draft gets a session of its own (listed under CLI sessions as *Request intake · agent · id*), continued on every pass, never lent to the agent's other work and not shared with other drafts — even for an agent set to a new session every time. It is retired when the request is approved or discarded. The session is a convenience only: every pass is self-contained. The agent reads the repository when one is chosen, and its prompt forbids changing anything. API-based agents work the same way without a session. Drafts are stored (`request_drafts`) and survive reloads; a draft left "analysing" by a restart is marked failed.

API: `GET /api/intake/agents`, `POST /api/intake/drafts`, `GET|DELETE /api/intake/drafts/:id`, `POST /api/intake/drafts/:id/refine` (`edits`, `add`, `note`, `reanalyze`), `POST /api/intake/drafts/:id/approve`.

## Human approval

A **Human approval** node (Workflow editor palette, or the *With human approval* template) puts you in the loop with the work actually running:

1. The engine starts your app (the node's *Start command*, else `npm run dev` / `npm start` from `package.json`), reads its address from its output (or the *Address* you set) and watches it.
2. The agent connected to the node (a QA, analyst, reviewer or developer; not the PM) reads your request, the files changed and the app's state and log, chooses the screens worth testing and writes a report: summary, what changed, what was tested, issues, app status.
3. The engine verifies the report itself: every proposed screen is requested, a page that answers 500 or doesn't answer is raised as an issue no matter what the agent claimed, and an app that isn't running is reported as *failed*. Only plain paths on the app's own address are accepted, never another site. Your own *Always offer these screens* list is included.
4. The first screen opens in your browser (turn it off in the node) and a **Needs you** item shows the report, an *Open* button per screen, the app log, and **Restart** / **Stop** for the app.
5. **Approve** follows the approve edge. **Reject with feedback** (required) follows the reject edge: connect it to the agent that should investigate and fix. Your words and what the app's log showed go to the agents, who investigate before changing anything; the fixed work comes back through the rest of the flow to a fresh review (the app is restarted). Rejection loops are bounded like any other (3 by default, then it asks you).

Every decision is recorded on the task (*Human review* panel, with round, decision and feedback), as a `human.decided` event and in Live activity. The app is stopped as soon as you decide, when the task is deleted or ends, when the run stops, and when the daemon exits; its full log is kept under the daemon's `app-logs` folder.

## Live activity

**Live activity** shows what each agent's CLI actually reports, parsed locally with no extra model calls:
- the prompt the agent received, and its messages;
- file reads, edits and searches, commands and test runs with their results;
- the CLI's own plan/todo updates, errors and the final result (cost, tokens, turns);
- hand-offs between agents.

Claude Code and cursor-agent `stream-json` are parsed; other CLIs (e.g. Devin) show their text lines. Reasoning appears only when the CLI emits it, labelled as such. Init records, heartbeats and rate-limit notices are kept in the **Technical log** tab. While a developer works in the repository, **Changes so far** shows its files with +/− counts, refreshed only when the working tree actually changes. **View diff** opens the green/red diff.

## Skills

Write general skills (reusable by any role) or role-specific ones on **Skills**, or import `SKILL.md` folders. Imported skills are scanned and need your approval; your own skills don't. Attach a skill to a role or to one agent. Unpinned attachments follow your edits. Each skill can be limited to kinds of work and/or task keywords, so it is sent only where relevant, within a per-prompt budget. Skills travel in the prompt, which works for every provider. Each work item records which skills were applied or skipped and why (`skill.applied`), and the Skills page shows when each was last actually delivered. Skills imported before content was stored are relinked by exact content hash from `~/.claude/skills` and similar folders (or re-import the folder; your approval is kept).

## Model routing

**Tier override.** The router normally picks the tier from what a work item is and how hard its task is. You can force it in two places: on a **workflow step** (Routing → the step's *Model tier*, custom workflows only) and on an **agent** (agent settings or Routing → *Model tier for this agent*, which also works in the read-only default pipeline). Precedence: the step's tier, then the agent's, then automatic. Each routing decision records where its tier came from.


Each agent has an ordered list of **model options** (Routing page; any backend from Providers, mixed freely). For every work item the router picks one:

1. Skip options that are unavailable: circuit open, quota window exhausted, or the account's monthly budget reached.
2. Work out the tier the work needs: `fast` (docs, failure analysis, difficulty-1 tasks), `standard` (most implementation, testing, PM prompts and acceptance), `strong` (difficulty 4–5). Risky work is never put on `fast`, however low its difficulty. That covers security-sensitive tasks (authentication, secrets, crypto, permissions, payments, injection), concurrency and hardware (interrupts, RTOS, DMA, firmware, races), data or API compatibility (migrations, breaking changes), and a fix or analysis after an earlier fix failed. The decision names the reason, e.g. `standard work (raised from fast: security-sensitive)`. A tier set on the workflow step or the agent still wins.
3. Among options at or above that tier, take the cheapest: plan-billed first (CLI logins, subscription/credit accounts — no per-call cost), then the lowest metered price; ties go to the least over-powered model, then list order. If nothing is strong enough, the strongest available.
4. If that call fails, the next option is tried, then other agents in the same role.

Synced models get a tier from their name (haiku/mini/flash/lite → fast, opus/max/high/ultra → strong, else standard); set it per model on Routing and the sync keeps your choice. Reasoning effort `auto` sets low/medium/high from the tier (API backends only). **Routing → fixed** turns per-task routing off: the first option is always tried first. Every choice is logged as a `model.routed` event and listed under **Recent routing decisions** — decisions made for a workflow node name the node.

**Routing follows the Workflow.** The Routing page's Flow strip and model panels are derived from the *saved active workflow* on **Workflow** — not a fixed list. The strip walks the graph from Start (branches stacked with their conditions, loops marked `↩ ×N`, message links, merge joins; bypassed nodes greyed); each step's agents and model tier are shown, and clicking a step opens `#/workflow` with that node selected. Model panels appear once per agent node in flow order, with a per-node **model tier override** and **budget (chars)** that edit the same `node.config` the Workflow inspector edits. Workspace agents that aren't on the canvas sit in a collapsed **Not in the workflow** section with an Add action (splices a pinned node before Done). Saving or activating a workflow updates an open Routing page within about a second. With no custom workflow active the strip shows the generated **Default pipeline** graph ("Clone it in Workflow to customize"), and a graph that fails validation falls back to that view with the problems listed. A few settings (prompt preparation, self-review) only affect the default pipeline — the page says so when a custom workflow owns the flow.

## Layout

- `daemon/` — TypeScript daemon: SQLite state (`node:sqlite`, WAL), hash-chained event log, workflow engine (`src/engine/` — fixed pipeline + the graph executor), workflow graph service (`src/services/workflow.ts` — validation, versioning, templates, estimates, audit), provider adapters (`src/adapters/` — scripted, openai-compatible, anthropic, cli, devin, manual), Git worktree manager, verification service, error-report KB, router (quota/circuit/SoD), approvals, usage accounting, REST + WebSocket API (`src/api/server.ts`). E2E demos: `npm run bench` (default pipeline), `node scripts/demo-workflow.mjs` (custom graph).
- `ui/` — React + Vite + Tailwind, styled after `spec/DESIGN-figma.md` (monochrome editorial frame, pastel color-block surfaces): Dashboard, Office (drag agents between role slots with permission-diff preview), Workflow (ReactFlow graph editor with live run overlay), Live Activity, Timeline & replay, Tasks kanban, DoD editor, Error Reports, Approvals, Agents, Skills, Providers.

- `daemon/data/` — runtime data (SQLite db, blobs, `secrets.json`); override the location with `OFFICE_DATA_DIR`. Git-ignored.

## State of the implementation

Working end-to-end (verified): run lifecycle draft → dod-review → running → done, deterministic checks (`exit0` commands plus `errors:open`, `review:all-merged-approved`, `sections(README.md,…)` rule checks), error reports with signature dedupe and KB-backed fix hints, analyst-routed fixes, separation of duties (author can't self-review), merge handling, pause/stop controls, usage/quota windows and circuit breakers, audit-grade hash-chained events.

Project types: stacks, domains and checks are detected from manifest files for Node, Python, Rust, Go, .NET, JVM/Android, Swift, Flutter, C/C++, embedded/IoT toolchains and game engines. Detected checks have a baseline, so only failures a task introduced gate it. Prompts carry the concerns of the project's domain. The repo tour follows Git's view and summarises large repositories by folder, key files and file types.

Efficiency: per-kind token report (`GET /api/runs/:id/token-report`, Dashboard panel) with cache-hit savings; budgeted prompts — stable prefix first, task-scoped context packs (the repo tour ships once per task), capped diffs/logs, low-value sections dropped and recorded on `prompt_versions`; result cache keyed on (kind, prompt, pack hash, model) reuses identical work items with zero adapter calls.

Communication: engine-built hand-off envelopes at every stage transition (the next agent gets the envelope, not the previous full output), strict-shape replies for PM/Prompt-Creator/reviewer/QA with one repair retry, broadcasts delivered to each agent at most once, near-duplicate messages dropped.

Reliability: failures classified transient / model-quality / fatal — backoff with jitter and provider failover, one repair retry then tier escalation, fatal pauses the run with one "Needs you" and a concrete fix; PM diagnosis step before human escalation (retry-stronger or split); per-task and per-run time/cost ceilings that pause, never kill; crash recovery requeues stale `running` items idempotently; timed-out CLI children are killed as a process tree on Windows.

Interventions: approval modes `always-ask` | `ask-when-risky` | `auto` with a change-risk classifier (out-of-scope files, config/secrets/lockfiles, deletions, large diffs, missing checks, user-owned edits); Needs-you grouped by run with approve-all-low-risk; tray notifications for needs-you/run-done/run-failed only; Dashboard digest "since your last visit".

Workflow: read-only lane — non-overlapping tasks draft/PM-review prompts on a desk while a writer holds the repo (`limits.maxReadOnly`, default 2; writers still never overlap); checks derived from acceptance criteria, non-checkable ones flagged at DoD; scope guard reports out-of-declared-path files to the PM; per-repo lessons memory (≤3, ~300 tokens, keyword/path match) injected into implement/fix prompts; model-free run summary on the run page with Markdown export.

Performance: benchmark `daemon/scripts/bench.mjs` — the scripted end-to-end scenario completes in ~27s (23 work items, 310 events, all 6 DoD items pass). Indexes on the hot lookups (`work_items(task_id,status)`, `agent_messages(run_id,read_at)`, `events(run_id,seq/ts)`, `work_items(cache_key,status)`, `error_reports(signature,status)`); agent names preloaded instead of per-message lookups; WebSocket broadcasts cap string fields at 2000 chars with lazy full detail via `GET /api/events/:seq`; recent-tree memoization + async git helpers keep snapshot/diff work off hot paths; Activity and Timeline cap rendered events and throttle WS-driven updates.

Remaining risks: the risk classifier and failure classifier are pattern-based — unusual provider error text degrades to transient retries (bounded, then PM diagnosis), and a novel risky change shape may pass `auto`; scope guard is advisory — the PM decides whether extra files belong; lessons match by keyword/path only, so relevant lessons can be missed; the read-only lane trusts `affectedPaths` for overlap — a task that under-declares its paths can draft against a stale tree; benchmarks use scripted agents, so real-provider latency dominates in production and the index/memoization wins matter most at scale.

Partial/scaffolded: sandboxing, hosted-agent adapters, embeddings/code intelligence, Tauri shell (browser UI used instead).
